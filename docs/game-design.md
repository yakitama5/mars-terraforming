# 火星開発ゲーム企画書

版番号 v0.4　更新日 2026年9月22日

研究方針の追補: 2026年10月20日。第3章に採用済みの共通研究ポイントと4分野を反映。
その他の最新の意向・実装状態は [project-memory.md](project-memory.md) を優先する。

国家を保有する国際宇宙開発機関を運営し、地球の都市と産業を育てながら火星の居住可能化を目指す、開発計画シミュレーション。研究、資金、製造、輸送、環境改変への投資を組み合わせ、自分の計画が街と惑星を変えていく過程を楽しむ。

FlutterSceneを利用し、iOSを先行公開、Androidは後から対応する。横画面固定、完全オフラインで遊べる放置型とする。本書は企画の基本方針と試作範囲、PCで実装を再開するための引き継ぎを整理したもの。確定事項と推奨案を区別し、個別の数値や未決定の詳細は実装・検証に向けて残す。

読む順番：1〜9章はゲーム企画、10章は出典、11〜17章はPCへの引き継ぎ。実装を始めるときは11・12・16・17章を確認する。

## 2 開発計画と街の運営
### 国家と街の運営

プレイヤーは、国家、国民、都市、ロケット基地を持つ国際宇宙開発機関。各国からの支援だけでなく、税収や事業収益を宇宙開発へ投じる。国家の成立背景、地理、名称は未決定。

手動で地区と主要施設を配置し、生活道路と一般住宅は自動で発展する。政策は税率、予算配分、産業支援までを扱い、外交は支援交渉などのイベントとして表現する。独立した外交管理システムは採用していない。

用途、施設規模、稼働配分、拠点間輸送の指定と、地形・近接施設による立地効果を推奨する。配置の細かさ、初期の人口・設備・資金は試作で仮設定する。開始時は小規模な研究・産業拠点で基本操作を学ぶ案とする。

### 科学的な土台と複雑さ

街の産業、資金の流れ、製造と輸送の関係は、可能な範囲で論文や事実を参考にする。序盤は現実の技術を想像できる施設、中盤以降は研究構想を拡張した設備、終盤はSFの未来技術へ進む。実証・構想・創作の区別を保つ。

管理項目は段階的に開放し、費用と効果、不足の原因を画面から把握できるようにする。部品や契約の細目は資材・能力などに集約し、開発を妨げている要因が理解できる粒度を推奨する。

### 採用する収益源

| 収益源 | 内容 | 開発計画との関係 |
| --- | --- | --- |
| 外部受注 | 工場・宇宙港の製造、打ち上げ、輸送 | 自前の火星計画と設備・人材を共用 |
| 技術の事業化 | 研究成果の製品化、技術提供 | 研究が次の収益事業を生む |
| 税収と施設収益 | 人口、商業、都市施設からの収入 | 生活基盤と産業を育てて財政を支える |
| 政府・企業の支援 | 指定された研究・開発目標への支援 | 自分の方針と支援条件を比較する |
| 宇宙産業 | デブリ清掃、宇宙観光など | 輸送・居住・回収技術を事業に展開 |

5種類を完成版の収益源に含める。宇宙産業の個別事業は研究と事業化を通して段階的に開放する案。上記はゲーム内事業の設計であり、個々の実在事業の成熟度や採算性を保証するものではない。

### 計画を制約するもの

推奨する管理資源は資金、資材、電力、人材、製造能力、輸送能力。資金と資材は蓄積する在庫、電力・人材・製造・輸送は期間内に使える能力として区別する。研究の知見は累積する。

受注を増やすと資金を得られる一方、火星へ送れる設備が減る。研究成果の製品化にも投資を必要とし、発見、事業化、宇宙への展開を別々の判断にする。税率や産業支援による人口・事業への影響は、理解できる少数の指標で示す案とする。

同じ研究が収益と火星開発の両方に役立つ構成を推奨する。例えば、デブリ回収技術は清掃受注と自分の輸送路の整備、居住技術は観光施設と火星拠点に展開する。研究だけで収益が発生するのではなく、設備と人材の配分を必要とする。

施設には維持費を設定する案。計画開始時には初期費用、継続費用、必要能力、予想成果を表示し、収益化までの運転資金を含めて判断できるようにする。

### 資金難からの再建

資金が尽きた場合は一部施設を休止し、基礎収入や再建支援によって立て直せるようにする。資金難による強制ゲームオーバーは設けない。再建支援の条件・額・頻度、休止の優先順位は未決定。

推奨案は、最低限の収入と再開手段が残る状態へ縮小すること。施設の休止、受注の見直し、再開に必要な資金を表示する。維持費だけが増え続けて再起不能になる状態や、支援の反復取得が最適な稼ぎ方になる設計を避ける。再建による停滞は残し、計画の立て直しを遊びに含める。

## 3 研究開発と宇宙輸送
### 研究計画の見通し

2026-10-20の追加指示により、最初は4分野と現在発見した候補だけを示す。
技術を解放すると次の候補と枝が現れ、未発見の分岐・総本数・将来の形は表示しない。
同日の追加評価により、研究の深さは左から右へ伸ばし、兄弟の部分木ごとに場所を確保する。
親を子群の中央へ置き、知識の幹から枝が分かれて育つ配置にする。
実行前に必要RPと解放内容を確認し、導入時に建設・運営の費用と負担を確認する。

### 共通研究ポイントと4分野（2026-10-20採用）

都市の施設へ研究者を配置して、全分野共通1種類の研究ポイントを生産する。
施設によって産出と運営負担を変え、資金を稼ぐことと研究を進めること、人材・外交や提携に関わる値等の
配分を都市開発の遊びにする。具体的な産出式・配分操作・施設ごとの数値は未決定。

研究の意味上の分類は「生命・生態／機械・制御／資源・材料／エネルギー」の4つを採用し、
画面ではカタカナの名前を使う。具体名の案は「バイオ／メカニクス／マテリアル／エネルギー」。
必要ポイントと前提を満たせば研究を必ず解放する。クリアまでに全研究の解放を要求せず、
多めの候補と複数の開発経路を用意する。早期発見の確率演出の有無・方法は未決定。

以前の「基礎研究→実証→小規模導入→大規模展開」を全技術共通の購入工程に固定しない。
研究の解放と実際の設備の建設・稼働を分け、必要な資源・輸送・生育環境等を使う段階で示す案。
実証を主要な応用の節目に絞るかなど、個々の前提は引き続き検討する。
研究の解放保証と、大規模な施策を実行する際の事故リスクは区別する。

今回の採用事項と残る判断は [decisions.md](decisions.md#2026-10-20-4分野共通研究ポイント解放保証の採用)。
論文をもとにした枝・個別技術の案は [研究ツリー拡張案](research-tree-catalog.md)、
確認範囲と成立条件は [出典台帳](research-literature.md) を参照する。
技術によって都市施設・ロケット等の設計や製法・運営方法を解放し、建設・製造・稼働へ投資する。
[解放先とバランスの案](research-unlocks.md)に全候補の対応を整理した。
少量輸送と大型機、輸入と現地生産、研究運転と商業生産を比較できる内容とし、
研究だけで設備・収益を無償付与しない。個別の施設・前提・数値は提案段階。
続く実装依頼により、上記の大枠をゲームへ反映した。実装・移行・仮値・検証範囲は
[共通RPと育つ研究ツリーの実装](research-implementation.md)を参照する。

### 科学資料の扱い

技術ごとに出典、研究年、実験・数値モデル・構想の別、成立条件、未解決点を開発資料へ記録する。
2026-10-20の追加指示により、ゲーム内の科学メモ・出典への導線は外す。
研究詳細の末尾には、その技術から想像する未来の生活を描いたオリジナルの短い文章を常時表示する。
費用、期間、成功率はゲーム用の設定値として管理する。

温暖化、生物の生育、人が呼吸して暮らせる環境は別の到達点である。温度の改善だけで居住可能と判定しない。菌類による建材研究を、火星屋外での増殖や全球温暖化の実証として扱わない。[S2][S3][S5]

軌道鏡や小天体導入などの古い構想は、当時の資源量や工学上の仮定も確認する。[S6] 終盤のSF技術にも必要資源、費用、設備、環境への作用を設定し、技術進歩と都市の未来感を結び付ける。実証されていない拡張にはゲーム上の仮定を明記する。

## 4 現実時間と放置中の進行
初回のメインED到達目標は現実の28〜42日。方法別の居住実績は途中の達成として配置する。重大事故や火星復元による追加日数は別途評価し、必ず42日以内に終わる保証とはしない。次の到達目安と、1日1〜2回・各数分の確認は、調整を始めるための仮定とする。

| 現実時間の目安 | 到達体験 |
| --- | --- |
| 初回10〜15分 | 最初の投資判断と、小さな研究・施設の完成 |
| 1〜3日 | 収益を次の研究に回す循環が成立 |
| 約1週間 | 火星の初期拠点と、複数の開発方針 |
| 2〜3週間 | 選んだ技術によって都市や火星の外観が変化 |
| 4〜6週間 | 全球の居住可能化を達成し、メインEDへ到達 |

### 時間設計の推奨案

時間換算は当初案の1週間＝10年に固定せず、遊びやすさに合わせて調整する。

まず研究・収益・建設・輸送を含めた到達日数を設計し、表示する年代と時間換算率を合わせる。基準となる時間倍率は調整用データに置き、研究だけでなく収支や輸送にも整合するように適用する。ゲーム内年数は現実の実現予測を表すものではない。

通常の研究は半日〜数日を中心に仮置きする。大事業は工程に分け、中間成果や追加判断を用意する。実行中も配置変更、次の投資の検討、研究説明の閲覧を行える。

### 予約と繰り返し実行

自動進行は開始・予約済みの作業を対象とし、繰り返し回数を選べるようにする。回数を制限せず、未選択の分岐へ到達するまで続ける指定も可能とする。未指定の研究や事業を自動判断で選び続ける方式にはしない。

操作例として、製造は指定回数、輸送は指定航路の反復、研究は予約済みの工程を分岐手前まで進める。完了済みの同じ研究を重複して完成させることはない。反復可能な作業・工程列の範囲、予約数の上限、分岐の定義は詳細設計で決める。

### 停止と再開の推奨案

分岐や新たな重大判断が生じた場合は、その計画だけを安全な状態で保留し、他の独立した作業を続ける。資金・資材不足、保管上限、輸送先の停止なども理由を表示する。条件回復時の自動再開と、確認が必要な停止を分ける。

収益の再投資上限、補給の優先順位、予備資金、事故時の対応を事前指定できる案とする。不在中に新規選択の操作期限が切れただけで重大事故になる仕組みは初期案に含めない。

一方、リスクを確認して実行した施策では、放置中も固有の重大事故が起こり得る。通常の不在対応と大規模計画のリスクを分ける。復帰時は収益、完了工程、事故、停止理由、判断待ちを短く報告する。通知は任意とする。

## 5 イベントと失敗と救済
### イベントの推奨案

地球と宇宙の出来事はゲーム内世界のイベントとして扱い、都市の特色、研究、開発段階に結び付ける。需要増加、共同研究、資源発見などの機会も用意する。

| イベント例 | 影響 | 判断の例 |
| --- | --- | --- |
| 地球の水不足 | 水循環技術への需要増加 | 地球への供給と火星への展開の配分 |
| 打ち上げ需要増加 | 外部受注の収益機会増加 | 受注、設備増設、自前の輸送 |
| 資源価格の高騰 | 製造費の増加 | 備蓄、代替素材の研究、延期 |
| 火星の砂嵐 | 発電や輸送の効率低下 | 備蓄、予備電源、稼働縮小 |
| 軌道設備の事故 | 輸送能力低下、デブリ増加 | 回収、迂回、安全設備への投資 |

### 施策ごとの失敗リスク

被害の大きさは施策ごとに設定し、火星全体の居住環境を失う重大事故も許容する。小天体を利用した環境改変では、投入の失敗が広範囲の環境を悪化させるゲーム上のリスクを設けられる。具体的な作用は出典と照合し、科学的に未検証の部分は創作として扱う。

結果を予定どおり完成、性能不足、遅延、一部損失、重大事故に分ける案とする。開始前に成功率、影響範囲、最悪時の被害、対策の効果を表示する。実証、小規模導入、予備設備でリスクと被害を変えられるようにする。

軌道事故はデブリ、環境改変事故は環境悪化や居住不能化など、原因に対応する影響を持たせる。失敗後は原因と得られた知見を示し、通常の修理・環境修復と、火星復元のどちらで立て直すかを考えられるようにする。

### 火星の復元

遡る時点を選び、火星の環境・施設・住民をその時点へまとめて戻す。資金と地球施設は現在の状態を維持する。研究成果と解除済み実績も保持し、報酬の再取得は認めない。

復元にかかる待ち時間は毎回固定とする。遡る長さや被害の大きさでは変えない。具体的な日数は未決定で、「1週間」は当初の候補にとどめる。初回4〜6週間とのバランスを見て調整する。

| 対象 | 確定した扱い |
| --- | --- |
| 火星の環境・施設・住民 | 選択した時点へまとめて復元 |
| 資金と地球施設 | 現在の状態を維持 |
| 研究成果・解除済み実績 | 保持し、同じ報酬は再付与しない |
| 復元待ち中の火星 | 進行を停止。次の計画の編集のみ可能 |
| 復元待ち中の地球・月 | 開発を継続 |
| 所要時間 | 毎回固定。具体的な日数は試作で調整 |

### 復元手順の推奨案

過去記録を選び、現在との差、失う設備・戻る設備、住民の変化、所要期間を確認して開始する。復元先は開始時に固定し、完了時に対象を一括適用する。待ち期間中に編集した計画は、復元後の設備・環境・必要資源を再確認して実行する。

火星停止中は生産、建設、研究、人口変化、環境変化、現地での資源消費を止める案。停止中の火星由来収入と維持費も止め、地球・月で進む収支とは分ける案とする。輸送の到着・受け渡しと軌道施設の範囲は未決定。過去の収益・支払い・輸送を再実行しない。

### 重複を防ぐための詳細設計

施設・住民を復元するだけでは、売却した施設の再換金や輸出済み資材の復活が起こり得る。資金と外部の進行を保持しつつ、同じ資産・住民・貨物・報酬の二重存在や二重取得を防ぐことを要件とする。時計変更の許容は維持する。

現地在庫と採掘済み資源の扱い、売却済み施設の再換金、火星から地球・月へ移住した住民、待ち中に到着する貨物は未決定。過去の火星を完全再現し、外部へ移した価値も保持するだけでは重複するため、対象の例外や取引上の制約を別途決める。資金の巻き戻しや自動清算を採用済みとは扱わない。

実装案は、対象の識別情報と移動・取引履歴を保持し、復元前後を照合する方式。記録範囲・頻度・保持期間、地形・地下資源、途中工程、復元後の再稼働条件を詳細化し、代表的な取引シナリオで確認してから復元機能を実装する。

## 6 実績とメインクリア
### 達成の構造

開発過程の成果を複数の実績として解除していく。ドームや地下都市、地域環境改変など、方法別の火星居住にも大きな実績を用意する。メインクリアは火星全球が地球のように暮らせる環境となることで、達成時にEDムービーを再生する。

「ハビタブルゾーン」は通常、恒星との距離に関する領域を指すため、本企画の目標は「火星全球の居住可能化」と表記する。[S8] 地球同様の生活を実現するという意図を、具体的な環境と生活の判定に落とし込む。

| 実績の分類 | 実績の例 | 位置付け |
| --- | --- | --- |
| 過程 | 初打ち上げ、初着陸、現地生産、月面拠点 | 進捗の実感と新しい目標 |
| 方法別の居住 | ドーム都市、地下都市、地域の環境改変 | 火星居住の大きな達成 |
| 環境と生活 | 水の安定利用、生育環境の成立、補給依存の低下 | 全球の居住可能化への進展 |
| メインクリア | 火星全球で地球のように暮らせる環境 | メイン実績とEDムービー |

実績名、個数、閾値、報酬の有無は未決定。すべての方法別実績をEDの必須条件にはせず、選んだ技術の組み合わせで全球の条件へ到達する設計を推奨する。

### メインクリアの条件

各地域に屋外で暮らせる範囲が広がり、火星全体として居住可能であることを条件とする。極地や高山のような過酷な地域は残っていてよく、陸地の全地点での屋外生活は要求しない。一地域のドーム完成や温暖化だけではメインクリアにしない。

環境を維持する大型設備が稼働し続けていてもよい。屋外生活ができ、必要な設備の維持も持続できれば達成とする。設備を停止しても自然環境だけで成立することは必須としない。

判定には温度、気圧、呼吸に適した大気、水、放射線への防護、生育環境、維持の持続性を組み合わせる案。地域区分、必要な居住可能面積、例外地域の扱い、閾値、安定期間、維持能力の評価方法は未決定。惑星平均だけで判断しない。

### エンディングの推奨案

火星の変化、育った街、人々の屋外での生活を見せるムービーを用意する。プレイヤーの主な実績や開発年表を最後に添える案。映像の尺、固定動画か端末内3D演出か、音楽や字幕は未決定。オフラインで最後まで再生できる構成にする。

達成時はクリア履歴と実績を保存し、再生済み状態も記録する。実績・ED鑑賞・過去の開発記録を共通の履歴として保持する。再生中の終了に備えて再視聴を可能にする案とし、達成履歴と現在の環境条件を分けて扱う。

### 継続プレイと引き継ぎ周回

ED後は同じ世界で都市拡張と未取得実績を続けられる。別の開発ルートを試す場合は、研究済み技術を引き継いで新しい周回を開始できる。資金と設備は初期状態へ戻す。研究時間短縮だけの特典へ置き換えない。

引き継いだ技術にも、実用化する施設、資源、輸送能力、環境条件を必要とする案。再研究を強制せず、何を先に実用化するかを周回の判断にする。実証の進捗・研究途中の成果・信頼性データの継承範囲、人口・環境・契約・予約の初期化、周回ごとの報酬を別途定義する。

28〜42日は初回EDの目標とし、周回は研究引き継ぎを前提に別途調整する。新規周回の開始確認と、元の世界を保存する枠・切り替え方法は要決定。

### 画面構成の推奨案

| 画面 | 主な操作と情報 |

FlutterSceneで惑星、拠点、都市の変化を描画し、計画・数値・操作パネルはFlutterのUIで構成する案とする。[S1] iOS実機の横画面で、3Dと操作パネルの共存、文字の読みやすさ、復帰時の動作を早期に確認する。

### データと進行処理

シミュレーションの状態、時間計算、画面表示を分離する。費用、期間、前提条件、リスク、実績条件はデータとして管理する。

保存対象は資源、施設、住民、研究、政策、契約、予約工程、反復回数・停止条件、環境、履歴、実績、ED状態、乱数状態、最終処理時刻、保存形式の版番号。火星の過去記録と、進行中の復元先・完了時刻、取引履歴も含める案。

周回IDと周回内の状態、引き継ぐ研究、共通の実績・ED・開発記録を区別する設計を推奨する。報酬ごとに共通・周回内・個別契約の取得単位を定め、火星復元で再取得させない。

再開時に経過分を計算し、工程完了、収支の変化、資源不足、事故などを時刻順に処理する。バックグラウンドでの常時実行に依存しない。復元やバックアップを含む保存では、世界状態を一貫した単位で記録する。

### オフライン保存と端末時刻

完全オフラインでのプレイと、端末内への自動セーブを基本とする。Googleアカウントとの紐付けは任意。未連携でも研究、イベント、実績、EDまで進められ、サーバー時刻や常時通信を要求しない。

時間経過は端末時刻に基づく。プレイヤーによる時計変更は楽しみ方として許容し、制裁や強制的なオンライン照合を設けない。負の経過時間、再処理による収益の重複、極端に長い経過での破損を避ける仕様は別途定める。

実装案として、時刻を戻したときは負の経過分を0とし、時刻の基準を取り直して将来の進行を継続する。イベントは処理済みIDとシミュレーション時刻を持ち、過去の完了を重複実行しない。端末時刻の具体的な再基準化は検証して確定する。

重要な操作後と一定間隔で自動保存し、直前の正常な保存を予備として保持する案とする。終了時だけの保存に依存せず、保存途中の終了からも復帰できるようにする。

### 任意のGoogleバックアップ

Google連携後に、手動または定期的なバックアップを利用できるようにする。バックアップと復元には通信が必要だが、通信や認証に失敗してもゲームは継続する。

保存先の候補はGoogle Driveのアプリ専用領域。Googleログインに加えて、保存用権限とアップロード・復元処理が必要である。具体的なAPIや認証ライブラリは未採用。[S9]

定期実行はOSと通信条件に左右されるため、指定時刻どおりの完了を保証しない。[S10][S11] 設定間隔で実行を試み、未実行なら次に通信と実行条件が整った機会へ繰り越す案とする。最終成功日時と未送信状態を表示する。

端末内セーブを基本に、一貫したセーブ一式を世代としてバックアップする案。火星の過去記録、共通履歴、周回状態、進行中の復元も含める。保持する世代数、容量、認証切れ時の対応は要決定。

別端末や過去のバックアップから戻す際は、内容と更新日時を比較し、現在の端末データを退避してから復元する案とする。複数端末の自動マージは未採用。Googleバックアップからセーブ全体を復元する操作と、ゲーム内の火星の環境・施設・住民を復元する救済を、別の機能として表示する。

## 13 実装を分ける単位とデータ設計

以下は実装上の推奨案。特定の状態管理ライブラリやクラス名を必須仕様としない。ゲーム進行の正しさを3D描画から独立して検証できる構造を優先する。

| 分担 | 主な責任 |
| --- | --- |
| ゲーム進行 | 収支、資源、施設、研究、予約、輸送、環境、事故、実績。Flutterに依存しないDart処理を基本にする |
| 操作の処理 | 建設・研究予約・反復変更・復元開始などを検証し、状態変更と履歴をまとめて反映する |
| 保存と外部連携 | 端末内保存、形式移行、バックアップ。Google連携はゲーム進行から分離する |
| Flutter UI | 目標・費用・稼働配分・停止理由・報告。表示値のために独自の収支計算を重ねない |
| FlutterScene | 惑星・地区・施設の見た目と選択操作。表示していない間も進行処理を扱える構造にする |
| コンテンツ | 施設、研究、契約、イベント、実績の定義と調整値。保存された進行状態とは区別する |

### 保存する状態の単位

共通履歴には実績、ED鑑賞、過去の開発記録、周回へ引き継ぐ技術を置く。周回状態には資金、政策、拠点、契約、予約、環境などを置き、周回IDで区別する。共通履歴も端末内データであり、オンラインアカウントを必須にしない。

地球・月・火星など拠点ごとの状態と、全体の資金・研究・輸送を分ける。火星復元用の過去記録は世界全体のセーブとは別に設計する。分けた状態を個別ファイルへ無計画に書かず、整合する一世代として保存する。

### コンテンツ定義に必要な項目

| データ | 最小限の定義案 |
| --- | --- |
| 施設・地区 | 固定ID、配置条件、費用、建設時間、消費と生産、提供能力、維持費、休止時の効果 |
| 研究・施策 | 固定ID、前提技術と設備、解放内容、所要時間、費用、実証、成功・失敗の効果 |
| 契約・輸送 | 固定ID、依頼内容、能力の占有、報酬と支払時点、出発地・目的地、途中状態 |
| イベント・実績 | 発生・解除条件、効果、選択肢、処理済みID、報酬の取得単位 |
| 科学資料 | 出典、研究年、実験・モデル・構想の別、成立条件、未解決点、ゲーム用の仮定 |

各数値に単位を持たせ、仮値であることを記録する。資金は最小通貨単位などの一定精度で扱い、丸め方を統一する案。研究IDや施設IDは表示名と分け、翻訳・改名でセーブが壊れないようにする。

## 14 放置進行・反復・保存の実装上の注意

### 時間処理と自動実行

予約から生じる工程には実行ID、対象拠点、状態、必要資源・能力、残り時間、反復指定、停止理由を持たせる案。有限回数と無期限を別の状態で表し、0回や異常値が意図しない無期限実行にならないようにする。未予約の分岐を勝手に選択しない。

再開時は工程完了、収支変更、資源切れ、事故などの境界まで時刻順に進める。毎秒・毎フレームの繰り返しで数年分を処理せず、変化のない区間は積算する。反復中でも資源・保管上限・能力・分岐による停止を飛ばさない。

同じ入力と同じ乱数状態なら、一度に進めた結果と分割して進めた結果が一致することを目標とする。乱数の利用順も保存・再開で重複しないようにする。長時間不在の切り捨て上限は未採用。処理負荷を下げる都合だけで経過時間や報酬を削らない。

費用の支払時点、能力の占有と解放、同時刻の完了・入金・維持費の処理順を決める。研究の二重予約・二重完了を防ぐ。資金不足は再建できる状態で停止理由を示し、独立した他の計画を続けられる設計を推奨する。

### 端末の時計と保存の一貫性

端末の時計変更は許容する。負の経過時間を0にすること、時計を戻した際の基準の取り直しは推奨案として検証する。過去に処理した入金や研究を再実行しない仕組みと、時計変更の禁止は別の話として扱う。

状態と最終処理時刻を同時に保存し、結果だけ保存・時刻だけ保存という中間状態を残さない。保存形式の版番号、コンテンツの版、周回ID、実行ID、報酬取得記録、乱数状態も検討する。読み込み直後の同時刻再評価で資金や報酬が増えないようにする。

保存は一時ファイルからの置き換えやトランザクションなど、採用形式に合う方法で一括確定する。前世代の正常データを保持し、破損時の回復と旧形式からの移行を用意する。認識できない新しい形式を初期データで上書きしない。

### オフラインとバックアップ

アプリ終了時に常時バックグラウンド処理が続く前提にしない。次の起動・復帰時に進める。完全オフラインで全ゲーム機能とEDを利用できるよう、必要なデータ・素材・説明を端末に用意する。外部論文リンクの閲覧とGoogleバックアップは通信する機能として分ける。

バックアップは整合した保存世代を送信する。Googleへのログイン成功とバックアップ成功を同じ表示にしない。定期実行の遅延、認証切れ、競合時は直近の成功日時と対応を示す。複数端末の自動マージは未採用で、初期案には含めない。必要性と復元方法は別途判断する。

## 15 火星復元・報酬・周回の境界

### 確定した仕様から外してはいけない点

火星の環境・施設・住民は選んだ時点へまとめて戻す。資金と地球施設、研究成果、解除済み実績は維持する。固定待ち期間中は火星を停止し、次の計画だけ編集可能。地球・月の開発は続ける。待ち時間の具体的な日数は未決定。

復元を単純な過去セーブの読み込みにすると、地球や資金まで戻るか、外へ持ち出した価値を二重に得られる。部分復元の境界を先に定義する。取引履歴や識別子は重複の検出に使えるが、検出後にどう扱うかというゲームルールの代わりにはならない。

### 復元機能の着手前に決める例

| 事例 | 未決定の判断 |
| --- | --- |
| 輸出済みの資材が火星の過去在庫にある | 在庫をどう戻すか。資源ごとの移動記録や復元例外の扱い |
| 売却済み施設が復元される | 同じ施設の再売却・再換金を認めないための制約 |
| 火星住民が地球・月へ移住済み | 外側の住民と復元対象の住民を二重存在させない扱い |
| 復元中に貨物が到着する | 待機、保管、受け渡しの扱いと、維持費・輸送能力への影響 |
| 採掘跡・地下資源・軌道設備がある | 地表環境以外の復元範囲と、資源の再採掘による価値の重複 |
| 研究・建設・輸送が途中だった | 過去の途中工程を戻すか、解除済み研究との整合をどう取るか |

資金の巻き戻し、自動的な差額徴収、復元施設の売却禁止などは、まだ採用していない。案を比較して決め、資金保持という確定条件との関係を記録する。未決定のまま「重複防止対応済み」としない。

### 実装の推奨案

復元処理に固有のIDと状態を持たせ、対象記録・固定待ち時間の開始と残り期間・完了反映を保存する。アプリ再起動で待ち期間を最初からやり直さず、完了は一度だけ適用する。現時点で保持すべき地球・月・共通履歴と、過去の火星の整合を同じ保存世代で確定する。

過去の火星に含まれる絶対時刻をそのまま再実行せず、途中工程を扱う場合は残り時間などへ変換する。待ち中に編集した計画は復元後の設備・資源条件で再検証する。停止中の維持費、収益、到着処理はルール確定後にそろえて実装する。

報酬は実績単位・周回単位・契約単位などの取得キーを定義する。通常の受注収入まで全期間で一度きりにせず、復元で同じ契約を再決済することを防ぐ。周回では研究済み技術を保持し、資金と設備を初期化する。途中研究、人口・契約等の初期化、元の世界の保存方法は決定待ち。

### 受け入れ確認の具体例

- **計画**：受注が設備を占有すると自分の開発が遅れ、配分を変更すれば進み方が変わる。税率や維持費の効果と停止理由を説明できる。
- **時間**：同じ開始状態を10回に分けて進めても一括で進めても、同じイベント条件なら結果が一致する。時計の前進・後退と非常に長い不在で保存が壊れない。
- **反復**：3回指定なら3回で止まる。無期限でも分岐・在庫・能力条件を超えて進まない。分岐待ちだけで他拠点の独立工程が止まらない。
- **保存**：入金直後・工程完了直後・書き込み途中で終了しても二重付与しない。旧形式移行、正常な予備データへの回復、同時刻での再読み込みを確認する。
- **復元**：地球・月は進み、火星は止まる。再起動後も待ち期間が続き、完了を一度だけ適用する。前章の輸出・売却・移住・到着の事例をすべて確認する。
- **達成と周回**：ドームや気温だけではメインEDを解除しない。EDを中断しても履歴と再視聴を保ち、新周回では研究を保持、資金・設備を初期化する。
- **通信と端末**：未連携・機内モードでも遊べる。Google認証失敗でセーブを失わず、バックアップから戻す前に対象を確認できる。iOS実機の横画面・休止復帰・描画負荷を確認する。

進行・保存の検証はGPUを使わない自動テストを中心に、描画・操作・性能はiOSで確認する。初回28〜42日は加速テストによる到達計算と実時間の試遊を分けて評価する。復元待ちを何度も使った際の停滞感も記録する。

### 決めるタイミング

仮の数値や内部構造は実装者が提案して検証を進めてよい。主要ゴールとオフライン方針は確定事項として維持する。資金保持と復元の関係など損失を変えるルールや収益化は、未決定の範囲を明記して判断する。後段の未決定事項のために最初の3D表示や財政試作まで止める必要はない。

研究の候補は、各技術の一次資料から説明カードを作りながら絞る。菌類を投入すれば呼吸可能な大気ができる、あるいは温暖化だけで地球同様になるとは設定しない。現実の研究の到達点とSFとして補う条件を示し、遊びの選択肢へ落とし込む。
